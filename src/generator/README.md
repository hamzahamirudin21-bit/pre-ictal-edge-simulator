# Module 1: Synthetic Signal Generator

EDUCATIONAL SIMULATION ONLY. All data is synthetic. This is NOT a medical device and makes no clinical claims. Do not use it for any medical decision.

This module is synthetic-only. Every sample is generated by code from a seed. No real sensor data and no patient data is used or collected. Every output object has `synthetic: true`.

It produces a synthetic PPG (photoplethysmogram) signal and a 3-axis accelerometer signal, plus a motion artifact in the PPG that follows the accelerometer z axis. "Pre-ictal-like" is a tunable simulation knob for teaching. It is not a clinical finding.

## Usage

```js
import { generateSignals } from './index.js';

const out = generateSignals({ seed: 7, durationSec: 30, preIctalLikeness: 0.5 });
// out.synthetic === true
```

`generateSignals` is pure and deterministic: no `Math.random`, no `Date.now`, no module-level mutable state, and it never mutates its input.

## Parameters

Omitted parameters take the defaults below. Ranges are inclusive.

| Parameter | Type / unit | Range | Default |
|---|---|---|---|
| `seed` | integer | 0 to 4294967295 | 1 |
| `durationSec` | number, s | 5 to 600 | 30 |
| `fs` | integer, Hz | 25 to 256 | 64 |
| `heartRateBpm` | number | 40 to 180 | 70 |
| `hrvSdnnMs` | number, ms | 0 to 150 | 50 |
| `preIctalLikeness` | number | 0 to 1 | 0 |
| `motionIntensity` | number | 0 to 1 | 0.2 |
| `tremorIntensity` | number | 0 to 1 | 0 |
| `orientation.pitchDeg`, `orientation.rollDeg` | number, degrees | -180 to 180 | 0, 0 |
| `artifactGain` | number | 0 to 1 | 0.5 |

`preIctalLikeness` is a simulation knob, not a clinical claim.

### Errors

Validation runs first (`validateParams` in `params.js`).

- `TypeError` for wrong types (for example a string for a number field, `null`, a non-object `params` or `orientation`).
- `RangeError` for values outside the range, non-finite values, and non-integer `seed` or `fs`.
- Messages name the field and its valid range, for example `fs must be an integer in [25, 256], got 64.5`.

## Output

```js
{
  synthetic: true, seed, fs, durationSec, n,       // n = round(durationSec * fs)
  ppg, ppgClean, artifact,                         // Float64Array(n)
  accel: { x, y, z },                              // Float64Array(n), in g
  beatTimes,                                       // Float64Array, seconds, strictly increasing
  meta: {
    effectiveHrBpm, effectiveSdnnMs, lfhf,
    clamped: { hr, sdnn },                         // booleans
    tremorBursts: [{ onsetSec, durationSec, freqHz }]
  }
}
```

- All signal arrays, including `beatTimes`, are `Float64Array`. `beatTimes` has variable length: beats are generated until the last beat time exceeds `durationSec`.
- `ppg` includes the motion artifact. `ppgClean` is the PPG before the artifact is added.
- `meta.tremorBursts` is `[]` when `tremorIntensity = 0`, because no tremor is added. Otherwise it is the full seed-determined burst schedule. The schedule (onsets, durations, frequencies, and the internal per-axis phases and gains) is derived only from the seed and `durationSec`. It never depends on `tremorIntensity`.
- The output does not expose gravity or other internals.

## Feasibility clamp (HRV)

With `k = preIctalLikeness`:

```
effHr     = min(hr * (1 + 0.1 * k), 180)
meanRrMs  = 60000 / effHr
sdnnCap   = min(150, (meanRrMs - 300) / 2.5, (2000 - meanRrMs) / 2.5)
effSdnn   = min(hrvSdnnMs * (1 - 0.5 * k), sdnnCap)
lfhf      = 1 + 3 * k
```

The cap keeps RR intervals inside [300, 2000] ms, so the RR clamp inside `generateRRSeries` is only a safety net and does not alter series for valid inputs.

`meta.clamped` reports when a clamp applied. Both comparisons are strict:

- `clamped.hr` is true when `hr * (1 + 0.1 * k) > 180`.
- `clamped.sdnn` is true when `hrvSdnnMs * (1 - 0.5 * k) > sdnnCap`.

`meta.effectiveHrBpm`, `meta.effectiveSdnnMs` and `meta.lfhf` report the effective values after the shift and the clamp.

## Pre-ictal-like knob

`preIctalLikeness` is a simulation knob for teaching. It is not a clinical claim. The constants below are illustrative simulation values. They are not fitted to clinical data, and no clinical source is claimed.

At `k = 1`, relative to `k = 0`:

- mean heart rate is raised by 10% (`HR_SHIFT_FRACTION = 0.1`), before the 180 bpm clamp;
- SDNN is reduced by 50% (`SDNN_REDUCTION_FRACTION = 0.5`), then capped by `sdnnCap`;
- LF/HF is `1 + LFHF_SLOPE * k` with `LFHF_SLOPE = 3`.

With respect to `k`, `meta.effectiveSdnnMs` is non-increasing, and `meta.effectiveHrBpm` and `meta.lfhf` are non-decreasing. At `k = 0` there is no shift.

## Motion artifact

```
dynZ     = accel.z - g_z                       (g_z = static gravity z from orientation)
smooth   = lowpass(dynZ)                       (zero-phase, single pole, 8 Hz)
artifact = artifactGain * 2.0 * smooth         (ARTIFACT_SCALE = 2.0)
ppg      = clamp(ppgClean + artifact, -3, 3)
```

- `dynZ` uses gravity subtraction on the fixed device z axis, not mean removal. With pitch `p` and roll `r`, `g_z = cos(p) * cos(r)`.
- The low-pass is a single-pole filter run forward then backward (zero phase). Its kernel is non-negative with unit DC gain, so a constant input is preserved.
- The artifact is a signed projection, not a magnitude.
- With `artifactGain = 0`, every `artifact` sample is exactly `+0` and `ppg` equals `ppgClean`.

Bounds:

- The dynamic part of each accelerometer axis is at most `0.5 (motion) + 0.15 (tremor) + 0.06 (noise) = 0.71 g` by construction, so `|dynZ| <= 0.71` and `|artifact| <= 2.0 * 0.71 = 1.42`.
- `|ppg| <= 2.92` is guaranteed (`ppgClean` clip 1.5 + `|artifact| <= 1.42`), and the typical bound by construction is 2.47.
- The `ppg` clamp at +-3, the `ppgClean` clip, and the IMU clamps (dynamic part at 0.75 g, output at +-4 g) are safety nets. They never act for valid inputs.

## IMU

- Units are g. Static gravity of magnitude 1 g is `[sin(p), -cos(p)*sin(r), cos(p)*cos(r)]` (pitch about y, then roll about x). With pitch and roll at 0 it is `[0, 0, 1]`.
- Motion: low-frequency sinusoids at 0.3 to 2 Hz, peak at most `0.5 * motionIntensity` g per axis.
- Noise: Gaussian clipped at 4 sigma, sigma = `0.005 + 0.01 * motionIntensity` g.
- Tremor: non-overlapping bursts, 3 to 6 Hz per burst, Hann envelope, amplitude `0.15 * tremorIntensity` g. At least one full burst lies inside the recording. The tremor term is exactly linear in `tremorIntensity` and exactly 0 at 0.

## Determinism and stream independence

Each component draws from its own stream, `createRng(deriveSeed(seed, label))`, with labels `'rr'`, `'ppg'`, `'motion'`, `'noise'` and `'tremor'`. `deriveSeed` is the only way sub-stream seeds are made.

- The same params give identical output.
- The draw count and order of the `motion`, `noise` and `tremor` streams never depend on the intensity parameters. The `rr` stream draws two phases plus one Gaussian per interval, and the `ppg` stream draws one phase plus two values per beat. For these two the count follows the number of beats, not the random values.
- Tested in `test/generator.test.js` ("stream independence"), for seeds 1, 42 and 1234 with a 10 s recording:
  - changing `tremorIntensity` does not change `ppgClean`, `beatTimes`, or the effective HR, SDNN, LF/HF and clamp values in `meta`;
  - changing `heartRateBpm`, `hrvSdnnMs` or `preIctalLikeness` does not change `accel`;
  - changing `motionIntensity` does not change `ppgClean` or `beatTimes`;
  - changing `artifactGain` does not change `ppgClean` or `accel`.
- Changing `tremorIntensity` changes accelerometer samples only inside the bursts, because the tremor term is zero outside them and the motion and noise streams are separate. This is asserted at the `generateIMU` level by the test 'tremor 0 vs 1: bit-identical outside bursts; D(1) is zero outside and non-zero inside' in `test/imu.test.js` (6 seeds, 20 s, 64 Hz). `generateSignals` passes the `generateIMU` arrays through unchanged as `accel`. The artifact and `ppg` follow `accel.z`, so they change with it.

## Performance

- `bandEnergy` in `spectrum.js` is a direct DFT with cost O(N x bins). Use short windows for spectrum analysis.
- `generateSignals` at `durationSec = 600`, `fs = 256` took about 0.2 to 0.4 s per call in a quick check on the dev machine (Node v24.22.0). This is machine-dependent.
